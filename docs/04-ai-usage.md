# 04 AI 使用

## 本人主导的工作

我负责项目的业务理解、需求拆解、验收设计和效果判断，并使用 AI 协助工程实现。

- 我选择题目 2，明确目标是帮助运营人员在预算和截止时间内形成可审核的内容活动方案，保存结果为草稿，不实际发布。
- 我将业务步骤拆解为素材检索、内容方案生成、成本与工时估算、约束检查和草稿保存，并明确预算与截止时间是不可擅自放宽的硬约束。
- 我依据题目要求确定验收场景，包括正常完成、信息不足、预算超限、截止时间紧、工具失败、重复执行和调用上限，并要求保留成功步骤、如实返回失败状态。
- 我检查测试结果和 Trace 是否支持这些验收判断，关注费用计算、失败后的动作变化、保存状态、重复提交结果及未完成状态是否准确。
- 我提供 GitHub 仓库和本地 API 配置来源，并要求凭据文件加入忽略规则、先交付基础版本再接入 API。

## AI 协助的工作

Codex 根据上述业务目标和步骤拆解，协助完成 Python CLI、决策循环、模型适配器、合成业务工具、JSON 草稿存储和自动化测试的工程实现。AI 也审阅了流程边界并提出改进，例如在保存前由 Agent 再次校验预算与截止时间、工具失败后把真实观察交回模型、保留已成功的素材结果，以及通过请求指纹实现重复提交幂等。

Codex 协助起草了 README 和 `docs/` 文档；我在检查后指出 AI 使用说明需要准确体现“本人主导、AI 辅助”，并要求修正文档中的贡献归属。文档没有把 AI 生成的代码表述为本人独立编写，也没有虚构人工逐行改动。

## 验收与验证

业务成功标准和结果判断由我负责；命令执行与运行材料由 Codex 在本工作区生成，我根据业务标准检查其结果。验证包括：

- `python -m unittest discover -s tests -v`：16 项测试通过，输出保存在 `examples/test-results.txt`。
- 检查离线 Trace 中预算从 12 单位超限后切换方案并以 8 单位保存；工具失败后更换生成模式；不可行方案明确未完成；重复执行只保留一条草稿。
- 使用本地忽略的 `apikey.txt` 实际运行三条模型决策路径，记录在 `examples/normal.apikey.output.json`、`examples/search-failure.apikey.output.json` 和 `examples/tool-failure.apikey.output.json`。其中两种不同工具失败分别触发检索策略和脚本模式调整。工具结果仍来自合成工具，不能据此声称已接入真实业务系统。
- 检查 `apikey.txt` 未被 Git 跟踪，且代码、测试和 Trace 中没有提交真实 API 密钥。

## AI 使用边界

离线 Mock 用于复现工具流程、约束和失败状态，不证明真实模型决策质量。三条真实模型 Trace 只构成有限样本，不能证明决策稳定性。AI 生成的代码和文档由我按业务验收标准审查；最终结论以可复现的测试和运行结果为依据。
